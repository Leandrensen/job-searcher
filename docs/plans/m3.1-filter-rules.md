# M3.1: One rules file applied at fetch, and the M3 review fixes

Base: commit `72f1424` on branch `feat/m3-ranking`. Executed with the `execute-plan` skill.

## Goal
1. Every job filter you control lives in one file, `config/job-filter-rules.json`: keywords, seniority, salary floor, excluded departments and excluded title words. It's applied **once, at fetch** (board discovery uses only the keywords; ATS storage uses all of them).
2. `npm run rank` no longer filters. It only orders open jobs by similarity to `config/search.md`.
3. Five review fixes:
   - duplicate jobs are no longer ranked;
   - a salary with an unknown period no longer excludes a job;
   - the model isn't loaded when there's nothing to rank;
   - a config error at the top level names `(root)` instead of a blank path;
   - rank failures are labelled by their cause.

### T3: The job filter rules and their example file
- Depends on: T2
- Files: `src/core/job-filter-rules.ts`, `src/core/job-filter-rules.test.ts`, `config/job-filter-rules.example.json`
- Interfaces:
  ```ts
  export const JobFilterRulesSchema = z.object({
    keywords: z.array(z.string().trim().min(1)).min(1),
    seniority: z.array(z.enum(SENIORITY_LEVELS)).min(1).optional(),
    salaryFloor: z.record(z.string().regex(/^[A-Z]{3}$/), z.number().positive()).optional(),   // yearly
    excludeDepartments: z.array(z.string().trim().min(1)).optional(),
    excludeTitleKeywords: z.array(z.string().trim().min(1)).optional(),
  }).strict();
  export type JobFilterRules = z.infer<typeof JobFilterRulesSchema>;
  export type RuleRejection = "keywords" | "title" | "department" | "seniority" | "salary";
  export type RuleInput = { title: string; departments: string[]; tags: string[]; salaryMin: number | null;
    salaryMax: number | null; salaryCurrency: string | null; salaryPeriod: string | null };
  export function matchesKeywords(job: Pick<RuleInput, "title" | "departments" | "tags">, keywords: readonly string[]): boolean;
  export function checkJobRules(job: RuleInput, rules: JobFilterRules): { pass: true } | { pass: false; reason: RuleRejection };
  ```
- Behavior:
  - `matchesKeywords`: the same haystack as `isTechJob` (title, departments and tags joined, lowercased, `-_/` replaced by spaces, whitespace collapsed). **Each keyword is normalized the same way** (lowercased, `-_/` replaced by spaces, whitespace collapsed), so `"full-stack"` in the file matches. Then it's tested as `(?<![a-z0-9])kw(?![a-z0-9])`, with the keyword regex-escaped. Descriptions are never read.
  - `checkJobRules` checks in this order and returns the first failure:
    1. `keywords`: no match.
    2. `title`: any `excludeTitleKeywords` entry matches the title, whole word and case-insensitive (`(?<![\p{L}\p{N}])kw(?![\p{L}\p{N}])` with flags `"iu"`).
    3. `department`: any `excludeDepartments` entry matches any department, the same way.
    4. `seniority`: the rule is set, `deriveSeniority(title)` isn't `null`, and the level isn't listed.
    5. `salary`: a floor exists for `salaryCurrency`, `salaryPeriod` isn't `null`, and `best = salaryMax ?? salaryMin` isn't `null`. `yearly = best × (year 1, month 12, hour 2080)`, and an unknown period string also skips the rule. It fails when `yearly < floor`.
- Failure cases: an empty keyword list is impossible (the schema has `min(1)`). Unknown seniority, salary, period or currency all pass.
- Example file: `config/job-filter-rules.example.json`. `keywords` is exactly today's `TECH_KEYWORDS`, in the same order: `"full stack", "fullstack", "front end", "frontend", "back end", "backend", "software engineer", "software developer", "web developer", "web engineer", "ui engineer", "ui developer", "product engineer", "javascript", "typescript", "js", "ts", "react", "react.js", "reactjs", "next.js", "nextjs", "node", "node.js", "nodejs", "martech", "marketing technology", "segment", "snowflake", "aws"`. After it: `"seniority": ["mid","senior","staff","lead"]`, `"salaryFloor": {"USD":60000,"EUR":55000}`, `"excludeDepartments": ["Sales","Marketing","Customer Success"]`, `"excludeTitleKeywords": ["Mobile","iOS","Android","Data Scientist"]`. Format it with 2-space indentation.
- Tests first (`job-filter-rules.test.ts`; `const KEYWORDS` is the example file's `keywords`, read with `fs`):
  - Port every case from `src/core/tech-filter.test.ts` to `matchesKeywords(job, KEYWORDS)`, with the same titles and the same expected booleans, including the department and tag matches, "never reads descriptions", and the `Segment Marketing Manager` false positive.
  - `every example keyword matches itself` (`it.each` over `KEYWORDS`).
  - `a hyphenated keyword matches`: `matchesKeywords({ title: "Full Stack Dev", departments: [], tags: [] }, ["full-stack"])` → `true`.
  - `checkJobRules` (`it.each`; the base is `{ title: "Senior React Developer", departments: ["Engineering"], tags: [], salaryMin: null, salaryMax: null, salaryCurrency: null, salaryPeriod: null }`, and `base rules = { keywords: ["react"] }`):
    - base → `{ pass: true }`;
    - title "Senior Accountant" → `"keywords"`;
    - `excludeTitleKeywords: ["React"]` → `"title"`;
    - `excludeDepartments: ["engineering"]` → `"department"`;
    - `seniority: ["mid"]` → `"seniority"`;
    - `seniority: ["senior"]` → pass;
    - the title "React Developer" with `seniority: ["mid"]` → pass;
    - `salaryFloor: {USD:60000}` with 50000 USD per year → `"salary"`;
    - with min 50000 and max 70000 → pass;
    - 6000 per month → pass;
    - 25 per hour → `"salary"`;
    - a EUR salary with only a USD floor → pass;
    - **59999 USD with a `null` period → pass** (an unknown period is skipped);
    - 1000 USD with period `"week"` → pass;
    - order: a job failing the keywords and the salary → `"keywords"`.
  - `the example file is valid`: `JobFilterRulesSchema.safeParse(<example JSON>).success` is `true`.

## Gotchas
- **Keep each commit green.** T5 and T6 keep a temporary fallback to `isTechJob` when no rules are passed, so the many existing tests keep passing until T9 removes it in one sweep.
- **The example keyword list must match `TECH_KEYWORDS` exactly.** Board fixture counts in `fetch-cli.integration.test.ts` (for example `EXPECTED_FIRST_RUN`) depend on it.
- **Tests use `keywordRules()` (keywords only), not `exampleRules()`**, unless a test is about the hard rules. Otherwise the example's seniority, salary and exclusion values would change unrelated expectations.
- **Never read `config/job-filter-rules.json` or `config/search.md` from the repo in tests.** They're personal and may exist on the machine. Always use temporary `configDir`s or the committed example.
- **Board discovery uses only `keywords`** (`runAdapter` with `techFilter`). Never apply seniority or salary to board postings; a company with a junior posting may still hire seniors.
- **A rule change closes jobs on the next fetch.** That's expected: closed jobs keep their row, embedding and future score, and reopen if the rule is loosened.
