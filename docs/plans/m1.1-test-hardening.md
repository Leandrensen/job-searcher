### T1: Runner survives a failing source (bug 1)
- Files: `src/sources/runner.ts`, `src/sources/runner.test.ts`
- Problem: `runSources` rejects as soon as any DB call inside one source throws (`latestPostedAt`, `upsertJobs` or `recordRun`). Every other source's summary is lost and the CLI crashes. A realistic trigger is a DB viewer holding a lock during a fetch.
- Behavior to implement:
  - Wrap the whole body of `runOne` (rate-guard check included) in `try/catch`.
  - **On an unexpected error `e`:**
    - Build a summary:
      - `status: "error"`
      - `error: "<e.name>: <e.message>"`
      - `inserted: 0`, `updated: 0`
      - `fetched`, `invalid` and `filtered` copied from the adapter result if `runAdapter` already finished, otherwise 0
      - `durationMs` measured from the start
    - Log `<id>: <error>`.
    - Try to `recordRun` with status `error` and that error string.
    - **If that `recordRun` also throws,** catch it, log `<id>: could not record run: <name>: <message>`, and still return the summary.
  - `runSources` must **never reject** because of one source. Other sources keep running and keep their results, in adapter order.
  - `upsertJobs` already runs in a transaction, so a failed upsert leaves no partial rows. Assert this.
- Tests first, in `runner.test.ts`. Use the existing `setup()`/`fakeAdapter()` helpers and `import { sql } from "drizzle-orm"`.
  - `isolates a DB write failure to its own source`:
    1. Create this trigger:
       ```
       db.run(sql`CREATE TRIGGER fail_remoteok_insert BEFORE INSERT ON jobs WHEN NEW.source = 'remoteok' BEGIN SELECT RAISE(ABORT, 'simulated write failure'); END;`)
       ```
    2. Run the `remoteok` and `jobicy` fake adapters.
    3. Assert:
       - results are `[["remoteok","error"],["jobicy","success"]]`
       - `results[0].error === "SqliteError: simulated write failure"`
       - `results[0].fetched === 2`, `inserted === 0`
       - `countJobs(db, "remoteok") === 0`, `countJobs(db, "jobicy") === 2`
       - the `fetch_runs` row for `remoteok` has `status: "error"` and that error text
  - `still resolves when recording the run fails`:
    1. Create this trigger:
       ```
       CREATE TRIGGER fail_runs BEFORE INSERT ON fetch_runs BEGIN SELECT RAISE(ABORT, 'runs table locked'); END;
       ```
    2. Run one fake adapter, passing `log` as a `vi.fn<(m: string) => void>()`.
    3. Assert that the promise resolves, that the job rows are still inserted, and that `log` was called with a string containing `could not record run: SqliteError: runs table locked`.
    4. The adapter's status may be `"success"` (insert worked) or `"error"` (recording failed). **Assert `"error"`.** If `recordRun` throws after a successful upsert, the summary becomes `error` with the `runs table locked` message, then the second `recordRun` attempt fails and is logged.

### T3: Invalid numeric entities (bug 3)
- Files: `src/core/text.ts`, `src/core/text.test.ts`
- Problem: `String.fromCodePoint` throws `RangeError` for code points above `0x10FFFF`. One bad entity silently drops the whole job, counted as `invalid`.
- Behavior: a numeric entity (decimal or hex) is decoded only when its code point is between 1 and `0x10FFFF` and **not** a surrogate (`0xD800`–`0xDFFF`). Otherwise the original entity text stays unchanged. Never throw.
- Tests first:
  - `leaves out-of-range numeric entities unchanged`: `"&#99999999;"`, `"&#xFFFFFF;"`, `"&#xD800;"` and `"&#0;"` each come back unchanged.
  - `decodes astral code points`: `"&#128512;"` → `"😀"`, `"&#x1F600;"` → `"😀"`.
  - `htmlToText does not throw on invalid entities`: `htmlToText("<p>a &#99999999; b</p>")` → `"a &#99999999; b"`.
- Verify: `npm test -- src/core/text.test.ts` passes.
- [x] Done

### T10: Extract `parseFetchArgs` and `runCli`, with unit tests for argument parsing
- Files:
  - `src/scripts/fetch-cli.ts` (new)
  - `src/scripts/fetch-cli.test.ts` (new)
  - `src/scripts/fetch.ts` (rewrite as thin wiring)
- Interfaces (`fetch-cli.ts`):
  ```ts
  export class CliUsageError extends Error {}           // name = "CliUsageError"
  export interface FetchArgs { sources: string[]; force: boolean }
  export function parseFetchArgs(argv: string[]): FetchArgs   // throws CliUsageError
  export interface SummaryRow {
    source: string; status: string; fetched: number; inserted: number; updated: number;
    invalid: number; filtered: number; ms: number; error: string;
  }
  export interface CliDeps {
    openDb: () => Db;                 // called ONLY after args are valid
    http: HttpClient;
    adapters: AnyAdapter[];
    now?: () => Date;
    out: { log(msg: string): void; error(msg: string): void; table(rows: SummaryRow[]): void };
  }
  export async function runCli(argv: string[], deps: CliDeps): Promise<number>   // returns exit code
  ```
- `parseFetchArgs` behavior:
  - `[]` → `{ sources: [], force: false }`
  - `--force` → `force: true`
  - `--source <v>`:
    - `<v>` is split on `,`, and empty parts are dropped
    - repeatable, and the results accumulate
    - duplicates are removed, keeping first-seen order
  - Errors, all thrown as `CliUsageError`:
    - `--source` as the last argument, or followed by a value starting with `--`, or a value with no non-empty parts (`","`) → message `Missing value for --source`
    - any other argument (an unknown flag or a positional value) → `Unknown option: <arg>`
- `runCli` behavior:
  1. Parse the arguments. On `CliUsageError`: `out.error(message)`, return 1, and **don't call `openDb` or fetch anything**.
  2. Validate every requested id against `deps.adapters`. If one is unknown: `out.error("Unknown source: <id>. Valid: <ids joined by ', '>")`, return 1, and don't call `openDb`.
  3. Select adapters **in registry order** (not argument order); select all if none were given.
  4. Call `deps.openDb()`, then `runSources({ db, http, adapters: selected, force, now, log: out.log })`.
  5. Call `out.table(rows)` with one `SummaryRow` per result. `ms` is `durationMs` and `error` is `error ?? ""`.
  6. Call `out.log("Total jobs in DB: <countJobs(db)>")`.
  7. Return 0 if any result is `success` or `skipped`, otherwise 1.

  Any other thrown error propagates to the caller.
- `fetch.ts` becomes only this:
  - Call `runCli(process.argv.slice(2), { openDb: () => openDb({ migrate: true }), http: createHttpClient(), adapters, out: { log: console.log, error: console.error, table: (rows) => console.table(rows) } })`.
  - Then `process.exit(code)`.
  - On rejection: `console.error(err)` and `process.exit(1)`.
  - No other logic.
- Tests first, unit tests in `fetch-cli.test.ts`. For the `runCli` validation tests, use `vi.fn()` for `openDb` and `out` callbacks only; no DB is needed.
  - `parseFetchArgs`: each case above gets its own `it`, about 10 tests.
  - `runCli returns 1 and does not open the DB for an unknown source`
  - `runCli returns 1 and does not open the DB for a usage error`
  - `runCli lists valid ids in the unknown-source message` (exact string)

## Gotchas
- **DB failure simulation.** `db.run(sql\`...\`)` with `import { sql } from "drizzle-orm"` works on the better-sqlite3 driver. Triggers live only in that in-memory DB, so they never leak between tests, because `setup()` creates a new DB each time.
- **T1 summary status.** When `recordRun` fails *after* a successful upsert, the jobs stay inserted (the transaction already committed) but the summary is `error`. That's intended: the run wasn't fully recorded.
- **T2 existing data.** Rows already in `data/jobs.db` keep their old `dedupe_key` until the next fetch updates them (the update path recomputes it). `duplicate_of` is **not** recalculated for existing rows. That's expected; don't write a migration.
- **T5 case sensitivity.** Removing the lowercase fallback means `&Amp;` (odd casing) stays undecoded. That's correct HTML behavior.
- **Fixture index.** In `remoteok.test.ts`, `items[0]` after `fetch` is `fixture[1]`, because the legal notice at index 0 is dropped.
- **Fixtures.** `himalayas/page1.json`, `arbeitnow/page1.json` and `getonboard/programming.json` must stay unchanged, because the paging tests rely on them announcing more pages. Use the new `*-last-page.json` files only for the integration routes.
- **Getting the full chain from one fixture.** The 6 Get on Board category URLs all map to the same fixture, so `fetched` is 24 and the in-run dedupe keeps 4. That's expected.
- **Registry order vs argument order.** `--source jobicy,remoteok` still runs `remoteok` first.
- **Timeout test.** It uses real timers. Don't use `vi.useFakeTimers()` with `AbortSignal.timeout`; it isn't driven by fake timers reliably.
